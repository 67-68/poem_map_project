# Prompt Engineering 原则：样例过拟合与对抗策略

> **适用场景：** AI 叙事生成器（事件 DSL 生成、NPC 对话、剧情文本）的 Prompt 设计。
> **核心问题：** 什么时候该给例子？怎么给才不会被 AI 降智？

---

## 1. 问题定义：样例过拟合 (Few-Shot Overfitting)

**现象：** 在"文本生成"场景（小说、文案、游戏叙事）中，当你给 AI 提供完整的文本样例后，AI 会像一条懒狗一样死死咬住样例中的句式、字数、甚至特定词汇组合。这被称为 **"样例过拟合 (Few-Shot Overfitting)"** 或 **"样例偏见 (Example Bias)"**。

**业界共识：**
- 对于「分类、信息抽取、JSON 结构化输出」——加例子是 **神器**
- 对于「文学/叙事生成（创造力和多样性要求高）」——加例子会导致 **严重的模板化副作用**

---

## 2. 五种对抗策略

### 2.1 骨架与规则样例 (Structural Abstraction)

**核心思想：** 不要给 AI 看完整的成品文章。只给它看"骨架"——结构规则、逻辑约束。

| | 做法 |
|---|------|
| ❌ 错误 | "请参考这个例子写一个事件：'你递上十文钱，门卫掂了掂，笑着让你进去了。'" |
| ✅ 正确 | "【结构要求】第一句：描写 NPC 刁难的对话。第二句：描写玩家模糊的物理交割动作（不要写出结果）。第三句：NPC 检查后的情绪反馈。" |

**本项目中的应用：** `narrative_constraint` 字段中的 `blind_box_transaction` 模式。

### 2.2 多样性对抗法 (The Diversity Shot)

如果非要给完整的文本样例，**绝对不能只给一个**；样例之间必须具有极大的差异性。

**原理：** LLM 是"模式匹配机"。给 1 个样例 → 复制粘贴；给 3 个差异极大的样例 → 学会提取公因式。

**实践：**
- 给一个字数极少的短例
- 给一个字数极多的长例
- 给一个语气极其严肃的例子
- 给一个语气极其搞笑的例子
- 明确告诉 AI："这些都是合法的输出，请保持这种**多样性**。"

### 2.3 反面教材机制 (Negative Prompting)

在文本生成中，**告诉 AI"不要做什么"往往比"怎么做"更有效。**

**实践模板：**

```text
【优秀示例】: "清客翻开你的布袋，除了几枚铜臭，竟无半张纸片，冷笑连连。"
    （原因：没有提前剧透包裹内容，动作和反馈分离）

【反面示例】: "你递上了没有装诗词的布袋，清客看了很不高兴。"
    （原因：行文干瘪，违背了盲盒交割原则，提前剧透了玩家没有诗词）
```

AI 对 `[Bad Case] + [Reason]` 的学习能力极强，能迅速避开模板化陷阱。

### 2.4 指令后置 (Recency Bias)

大模型具有 **"近因效应 (Recency Bias)"**。如果把长长的例子放在 Prompt 的最后面，AI 的注意力会被例子完全吸走，忘记开头定下的基调和规则，变成无脑复读机。

**业界标准排版顺序：**

```text
1. 角色设定 (Persona)
2. 样例展示 (Examples)
3. 核心任务与强约束条件 (Task & Constraints)  ← 永远放在最后一行！
```

### 2.5 零样本提示 (Zero-Shot Strong Constraints)

当你的场景极度渴求**文本的多样性、文学性、出乎意料的戏剧张力**时，不给任何文本例子，而是通过**极度详尽的维度约束**来榨取 AI 内部已有的庞大知识库。

**约束工具包：**
- 五维宪法 (Five Dimension Constitution)
- 情绪矩阵 (Emotion Matrix)
- 视角限制（如：必须用第二人称"你"）
- 修辞要求（如：必须包含视觉和触觉描写）
- 叙事设计模式（如：盲盒交割原则）

## 3. 本项目中的架构建议

在你的大唐叙事生成器中，不同内容类型需要不同的策略：

| 内容类型 | 策略 | 原因 |
|----------|------|------|
| **JSON 格式 / DSL 语法**（如 `prop_add`） | **必须给例子 (Few-Shot)** | Godot 引擎会解析报错，需要严格照抄格式 |
| **`description` / `narrative_result` 等文学文本** | **坚决不给完整文本例子** | 改为提供"叙事设计模式"（如盲盒交割原则、维度描述约束） |

**总结公式：**

> 用逻辑和结构去**束缚**它的格式，用留白和约束去**解放**它的文笔。

---

## 4. 快速决策树

```
需要生成什么？
├── 结构化数据 / DSL 代码
│   └── ✅ 给 Few-Shot 例子（格式 > 多样性）
│
└── 文学叙事 / 对话文本
    ├── 文本多样性要求高？
    │   ├── ✅ Zero-Shot + 维度约束
    │   └── 或 ✅ Structural Abstraction（只给骨架）
    │
    ├── 必须给例子？
    │   └── ✅ Diversity Shot（至少 3 个差异极大的样例）
    │
    └── 是否已知常见的失败模式？
        └── ✅ Negative Prompting（反例 + 原因）
```

## 6. 进阶案例研究：样例污染 (Few-Shot Pollution) 与动作空间升维

> **场景：** 你的叙事生成器需要让 NPC 以不同方式侮辱/销毁玩家的诗稿。
> **问题：** 你在 JSON 约束中写了"引火"，在 CSV 例子中喂了 9 条"引火 / 炭火 / 烧火"语料。
> **结果：** AI 像个无情的锅炉工，从头到尾只会生火。

### 6.1 问题定义：样例污染 (Few-Shot Pollution)

**现象：** 当你在 prompt 的多个层级（L0 门槛约束、TypeB/C 叙事约束、Few-shot 样例）中**高频使用同一个具象动作词汇**时，AI 的注意力权重会直接坍缩到这个局部最优解上。这不只是样例过拟合——这是**跨层级的污染叠加**。
**你应该抽象这个动作的定义，尽可能从多个角度描述这个抽象的动作，然后再给出多个例子**
**你应该抽象这个动作的定义，尽可能从多个角度描述这个抽象的动作，然后再给出多个例子**

**与普通样例过拟合（第 1 节）的区别：**

| 维度 | 样例过拟合 (Few-Shot Overfitting) | 样例污染 (Few-Shot Pollution) |
|------|-----------------------------------|-------------------------------|
| 范围 | 单一样例的句式/字数被复制 | 同一动作词汇跨多个 prompt 层级高频出现 |
| 原因 | 样例太少或样例太单一 | 约束层级之间缺乏抽象隔离 |
| 后果 | 输出模板化 | 输出陷入单一动作死循环 |
| 解法 | 增加多样性 / Zero-Shot | 升维约束 + 语料强力洗牌 |

### 6.2 核心诊断：标量约束 vs 向量约束

你的问题不在于"约束后的空间太小"，而在于**你给出的约束是标量（具体的"引火"动作），而不是向量（抽象的"侮辱/销毁"动作空间）**。

| 约束类型 | 定义 | 示例 | 后果 |
|----------|------|------|------|
| **标量约束 (Scalar)** | 指定一个具体的动作实例 | `"门子把诗拿去引火了"` | AI 变成复读机，只会生火 |
| **向量约束 (Vector)** | 定义一个抽象的动作空间 + 多样性要求 | `"诗在NPC眼里只是任意一种低贱的日常消耗性纸张（垫桌角、包垃圾、擦拭污物等）。严禁重复使用相同的消耗方式。"` | AI 在动作空间中自由采样，输出多样化 |

### 6.3 解决方案：动作空间升维 + 语料洗牌

#### 6.3.1 切除 Few-shot 毒药（语料洗牌）

CSV 例子绝对不能全是一个套路。保留一个"引火"，其余必须强制替换为不同维度的消耗方式。

> **动作空间扩展示例（底层文盲的纸张消耗场景）：**
> - 用来包残羹冷炙（沾满油污）
> - 用来垫缺了角的桌腿（物理践踏）
> - 揉成一团用来擦拭门槛上的鸟粪（排泄物羞辱）
> - 糊窗户挡穿堂风（工具化无视）

#### 6.3.2 JSON 节点热更新（约束升维）

将 JSON 中硬编码了具体动作的地方，用更高抽象层级的描述替换。

**示例 1：L0 门子约束重构**

```json
{
  "dimensions": {
    "gatekeeper_level": {
      "L0": {
        "narrative_constraint": {
          "before": "门子把诗拿去引火了",
          "after": "门子索要门包或名帖，以物理阻挡为手段。NPC 是底层文盲，看不懂诗，诗在他眼里只是任意一种低贱的日常消耗性纸张（如：垫桌角、包垃圾、擦拭污物等）。严禁在不同事件中重复使用相同的纸张消耗方式。"
        }
      }
    }
  }
}
```

**示例 2：TypeC 才华剥削约束重构**

```json
{
  "dimensions": {
    "extraction_type": {
      "TypeC": {
        "narrative_constraint": {
          "before": "NPC 把诗拿去烧掉",
          "after": "NPC 掠夺或改造玩家的诗——或沦为粗鄙的日用废纸、或被篡改得面目全非、或剥夺署名权。呈现的是才华被无情吞噬的过程。必须根据不同 NPC 的身份阶层，随机选择完全不同的剥削手段。"
        }
      }
    }
  }
}
```

#### 6.3.3 注入反重复指令 (Anti-Repetition Directive)

在 JSON 或 prompt 的最上层，增加强制性的系统级多样性要求：

```json
{
  "anti_repetition_directive": "极度痛恨重复的意象表达。在生成变体时，绝对禁止在同一批次内复用相同的隐喻（特别是'引火'、'烧炭'等动作）。必须在物理损坏、生活消耗、结构性无视等维度中强制跳跃。"
}
```

### 6.4 架构原则再审视：契约即自由 (Paradox of Constraint)

这个案例完美验证了"约束的悖论"：

- **做对的事：** 把动作限定在"NPC 被动回应"、"递上"，不许有上帝视角心理描写——这是**高明的约束**，保证了文风的冷峻感。
- **做错的事：** 替 AI 把具体动作想死了——这是**越权的约束**，扼杀了多样性。

**正确的做法：** 钉死大方向（如"轻蔑的毁坏"），告诉 AI"我不接受重复的毁坏方式"，然后把它一脚踹进动作库的词海里。

> 就像微服务里的接口定义：规定好入参（诗稿）和出参（被侮辱的剩余物），中间是在引擎里切碎、揉皱、还是拿去垫桌脚的，交给具体实现的黑盒去发散。

### 6.5 快速诊断清单

当你的 AI 输出出现"动作死循环"时，按此清单排查：

- [ ] 同一个动作词汇在几个不同的 prompt 层级中出现？
- [ ] Few-shot 样例中有多少条使用了相同的动作？
- [ ] JSON 约束定义的是具体动作（标量）还是抽象动作空间（向量）？
- [ ] 是否有反重复指令（anti-repetition directive）？
- [ ] 不同 NPC 身份阶层是否映射了不同的动作空间？

## 7. failed_hint 核心原则：因果归责 (Causal Attribution)

> **关键词：** 这是你自己的选择 -> 导致了这个性格 -> 导致了这件事情发生。

### 7.1 问题定义

`failed_hint` 不是「补充说明」也不是「环境描写」。它的唯一职责是：**让玩家在这一刻感受到——"因为我选择了这条路，所以我今天站在这里，只能看着，不能动。"**

一个糟糕的 `failed_hint` 是「无关紧要的补充」——它只是描述了角色当下的犹豫、克制、或环境氛围，但没有把因果链拉回玩家的选择。

### 7.2 因果链模型

```
玩家的历史选择
    │
    ▼
当前的人格/性格 (trait)
    │
    ▼
面对这个时刻的无力 (failed_hint)
```

`failed_hint` 必须同时触及两层：
1. **性格层**：因为你不是狂客 / 因为你是低旷达 / 因为你选择了算计 —— 这是你现在的样子
2. **后果层**：所以这个动作你做不了 / 这句话你说不出口 / 这个机会不属于你 —— 这是你现在的处境

### 7.3 诊断标准：好 hint vs 坏 hint

| | 好的 `failed_hint` | 坏的 `failed_hint` |
|---|-------------------|-------------------|
| 因果链 | 性格 → 无力 → 此刻 | 只有"此刻" |
| 玩家感受 | 「是我自己选的」 | 「作者在补充背景」 |
| 叙事位置 | 插在因果链中间 | 浮在场景表面 |

**[Bad Case]** (无关紧要的补充):
> "他站在门槛内，想迈出那一步，却想起昨夜咳出的血丝，于是退回屋里，轻轻掩上了门。"

为什么坏？它只描述了"他犹豫了"。玩家不知道这是自己选的。咳出的血丝是生理细节，不是性格因果。

**[Good Case]** (因果归责):
> "他看见李白扔过来的酒壶——手已经伸出去了。但他不是一个不计后果的人。他的手在袖口里攥紧，酒壶落在地上。"

为什么好？三件事发生：(1) 本能想接 → (2) 但他不是那种人 → (3) 酒壶落地。每一步都在说：**这是你选的性格，这是你选的后果。**

### 7.4 写作铁律

```
1. 必须出现「但是/但/却/不是」——转折词是因果链的铰链
2. 必须包含性格判断——「他不是那种人」「他没有那种疯劲」「他选择了计算」
3. 必须出现一个未遂的动作——手伸出去但收回、话到嘴边但咽回、脚迈出去但转身
4. 禁止纯环境描写、禁止纯生理反应、禁止没有性格判断的犹豫
```

### 7.5 与反面教材机制的关系

`failed_hint` 遵循本文档第 2.3 节的反面教材机制——给 AI 同时提供 `[Bad Case] + [Reason]` 比单纯的正面指令有效十倍。在 `failed_hint_plugin.py` 的 prompt fragment 中应注入 `[Bad Case]` + 对应的因果链断裂原因。
